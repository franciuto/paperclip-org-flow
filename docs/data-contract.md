# Data contract

The contract between worker and UI lives in a single file: `src/shared/types.ts`. Everything it contains crosses the worker → host → browser bridge, so it is plain JSON: no `Date`, no `Map`, no functions.

General rules:

- Dates are ISO 8601 strings (`"2026-03-10T00:51:12.345Z"`).
- Person id: the agent's UUID for agents, `user:<userId>` for the board's human users.
- Percentages are integers from 0 to 100.
- User-facing labels are in English and are produced by the worker (`stateLabel`) or by the UI.

## Activity feed

### `Party`

A person involved in an event, as the event names them.

| Field | Type | Meaning |
| --- | --- | --- |
| `kind` | `"agent"` \| `"user"` | agent or human user |
| `id` | string | id of the agent or user **without** the `user:` prefix |
| `name` | string, optional | name added by the worker; for users it is always `"Board"` |

It can be `null` (nobody, for example a task with no assignee). In the activity feed users have the raw id; in the snapshot they have the prefixed id. The UI reconciles them with `resolveParty` (`src/ui/presence.ts`).

### `FeedKind`

| Value | When |
| --- | --- |
| `handoff` | the assignee changed (agent ↔ agent, agent ↔ user) |
| `status` | the status changed, the assignee did not |
| `created` | task created |
| `run_started` | an agent started a run |
| `run_finished` | run finished successfully |
| `run_failed` | run failed or timed out |
| `progress` | percentage reported with `report_progress` |
| `ping` | test event, generated by the `ping` action |

Cancelled runs (`agent.run.cancelled`) close the run in progress but do not produce a record.

### `FeedRecord`

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | id of the Paperclip event (`eventId`), or a UUID generated for `progress` and `ping`. Unique: the UI deduplicates by this |
| `at` | ISO string | when it happened (`occurredAt` of the event) |
| `kind` | `FeedKind` | kind |
| `issueId` | string \| null | id of the task, if any |
| `identifier` | string \| null | readable identifier, e.g. `ACME-62` |
| `title` | string \| null | title of the task |
| `parentId` | string \| null | id of the parent task, if known; used to colour the record |
| `from` | `Party` | for `handoff`: who had the task |
| `to` | `Party` | for `handoff`: who receives it; for `created`: the initial assignee |
| `actor` | `Party` | who performed the action (for runs: the run's agent) |
| `statusFrom` | string \| null | previous status, if it changed |
| `statusTo` | string \| null | new status, if it changed; for `created`: the initial status |
| `percent` | number \| null | for `progress` |
| `note` | string \| null | for `progress`, the agent's note |

A `handoff` can also change status in the same event (e.g. handoff to the reviewer with `statusTo: "in_review"`).

## Snapshot

The snapshot is the complete state of a company at a given instant. It is produced by `deriveSnapshot` (`src/worker/snapshot.ts`).

### `VisualState` and `Pose`

Visual states of a person and the associated Paperclip character pose (`POSE_FOR_STATE`):

| State | Pose | In brief |
| --- | --- | --- |
| `working` | `working` | run in progress |
| `thinking` | `thinking` | holds a task that is `in_review` |
| `listening` | `listening` | has just received a task |
| `success` | `success` | has just closed a task |
| `confused` | `confused` | error, failed run or task sent back |
| `sleepy` | `sleepy` | nothing to do for a while |
| `idle` | `idle` | has tasks to do, or is free |
| `paused` | `rest` | agent paused or terminated |
| `waiting` | `idle` | human user with tasks waiting on them |

The exact rules are in [states-and-percentages.md](states-and-percentages.md). The available poses are `rest`, `idle`, `listening`, `thinking`, `working`, `success`, `confused`, `sleepy`.

### `PersonView`

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | UUID of the agent or `user:<userId>` |
| `departmentId` | string \| null (optional) | the person's department (`DepartmentView.id`); `null` for top-level agents, users and terminated agents |
| `kind` | `"agent"` \| `"user"` | |
| `name` | string | name of the agent; for users `"Board"`, `"Board 2"`, … in id order |
| `title` | string \| null | the agent's title in Paperclip; if empty, the label of the Paperclip role (`AGENT_ROLE_LABELS`, e.g. `ceo` → "CEO"); `null` if the role is missing too. Shown under the name in the org chart |
| `role` | string \| null | role of the agent |
| `reportsTo` | string \| null | id of the manager. `null` for top-level agents, for users and when the manager is not among the people shown |
| `paletteId` | string \| null | character palette (`appearance.paletteId`); `null` for users |
| `customAvatarUrl` | string \| null | `/api/assets/<id>/content` if the agent has an uploaded photo; the UI prefers it over the character |
| `agentStatus` | string \| null | raw Paperclip status (`idle`, `running`, `paused`, `error`, `terminated`, …); `null` for users |
| `state` | `VisualState` | computed visual state |
| `stateLabel` | string | short label under the title (under the name if the title is missing), e.g. `"Working on ACME-62 · 40%"` |
| `stateSince` | string \| null | since when the state has held, when meaningful |
| `activeTaskId` | string \| null | task the state refers to |
| `lastActivityAt` | string \| null | last known activity (history, run, heartbeat) |
| `stats` | `{ received24h, passed24h, closed24h }` | tasks received, passed on to others and closed in the last 24 hours (from the plugin's history) |

Terminated agents appear only if they still hold a task. Users appear only if they have a task (open or recently closed).

### `TaskView`

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | id of the task |
| `identifier` | string \| null | e.g. `ACME-62` |
| `title` | string | title, `"(untitled)"` if missing |
| `status` | string | Paperclip status (`backlog`, `todo`, `in_progress`, `in_review`, `blocked`, `done`, `cancelled`; other unknown statuses are treated as open) |
| `priority` | string \| null | Paperclip priority |
| `holderId` | string \| null | person id of the assignee |
| `parentId` | string \| null | id of the parent; `null` also when the parent is not readable |
| `groupId` | string | colour group: id of the parent, id of the task itself if it is a parent, or `"standalone"` |
| `progress` | number | 0–100 |
| `progressSource` | `ProgressSource` | where the percentage comes from |
| `progressNote` | string \| null | the agent's note, only with `reported` |
| `updatedAt` | ISO string | last update of the task |
| `bounces` | number | how many times the work came back (rules in [states-and-percentages.md](states-and-percentages.md#bounces)) |
| `journey` | `JourneyStep[]` | who had it, oldest first; partial for tasks born before 1.0 |
| `closedAt` | string \| null | closing date for `done`/`cancelled` tasks that are still visible |

### `GroupView`

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | id of the parent task, or `"standalone"` |
| `identifier` | string \| null | identifier of the parent |
| `title` | string | title of the parent; `"Standalone tasks"` for `standalone`; `"Parent task"` if the parent is not readable |
| `color` | string | CSS colour `oklch(...)` stable per id; neutral `oklch(62% 0 0)` for `standalone` |
| `status` | string \| null | status of the parent |
| `progress` | number | closed children / total children × 100, cancelled excluded; 100 if the parent is `done` |
| `childrenTotal` | number | total children (cancelled excluded), including those outside the visible window |
| `childrenDone` | number | `done` children |
| `holderIds` | string[] | people who hold open tasks of the group |
| `updatedAt` | string \| null | most recent update among the parent and the group's tasks |

The worker sorts the groups (open first, then by most recent update, `standalone` last); the UI re-sorts them by identifier (`sortGroups` in `src/ui/model.ts`).

### `OrgFlowSettings`

| Field | Type | Default | Limits |
| --- | --- | --- | --- |
| `sleepAfterMinutes` | integer | 15 | 1–1440 |
| `keepClosedHours` | integer | 24 | 0–720 |
| `enableSimulation` | boolean | true | |
| `departmentNames` | `Array<{ lead, name }>` (optional) | `[]` | `lead` and `name` non-empty, `name` at most 60 characters |

Details in [installation.md](installation.md#settings).

### `DepartmentView`

Paperclip has no departments: the worker derives them from the reporting line (`src/worker/departments.ts`). A department is the subtree under each direct report of a top-level agent (an agent with no manager, such as the CEO; if there is more than one top-level agent, each opens their own departments). Agents with a missing manager or in a reporting cycle count as top-level agents. Top-level agents, users and terminated agents have no department.

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | id of the department lead |
| `name` | string | displayed name |
| `leadId` | string | id of the lead |
| `memberIds` | string[] | the lead and all their reports (agents only), from the lead downwards |

The name comes, in order: from the `departmentNames` setting (matching the lead's id or name, case-insensitive); from keywords in the lead's title (for example `graphic`/`design` → "Graphics", `communication`/`marketing` → "Communications", `CIO`/`CTO`/`IT`/`system`/`network`/`devops` → "IT and infrastructure", `librarian`/`knowledge` → "Library", then Administration, Sales, Development, Legal, People); from the role (`designer`, `cmo`, `cto`, `devops`, `engineer`, `researcher`); otherwise "<name>'s team". If two departments have the same name, " · <lead's name>" is added to both. Example: a CEO with three direct reports gives three departments, each with its lead and the lead's reports; the CEO and the board have no department.

### `Snapshot`

| Field | Type | Meaning |
| --- | --- | --- |
| `companyId` | string | company |
| `generatedAt` | ISO string | version of the snapshot; changes only when the content changes |
| `people` | `PersonView[]` | agents in Paperclip order, then the users |
| `tasks` | `TaskView[]` | open tasks + those closed in the last `keepClosedHours` hours |
| `groups` | `GroupView[]` | one group for each parent present, plus `standalone` |
| `feed` | `FeedRecord[]` | most recent first, at most 100 |
| `settings` | `OrgFlowSettings` | settings in force |
| `departments` | `DepartmentView[]` (optional) | departments derived from the reporting line; absent in earlier workers |
| `counts` | `{ working, thinking, sleepy, waiting, open, closed24h }` | people per state, open tasks, tasks closed in the last 24 h |

The page and the widget recompute the counters with `liveCounts` (`src/ui/model.ts`) to account for local effects; of `counts` they use only `closed24h`. Note: in `counts.waiting` the worker counts the people in the `waiting` state, while `liveCounts` counts the open tasks held by users.

## Bridge keys

The bridge goes through the Paperclip server:

- data: `POST /api/plugins/<pluginId or key>/bridge/data`
- actions: `POST /api/plugins/<pluginId or key>/bridge/action`

Body: `{ "key": "...", "companyId": "...", "params": { ... } }`. The host checks access to the company, then passes `companyId` to the worker together with the `params`; the host's one takes precedence over any `params.companyId`. A successful response is always wrapped in `{ "data": ... }`. Worker errors come back as HTTP 502 with `{ "code": "...", "message": "..." }`.

It works with a board API key as `Authorization: Bearer`. Ready-made `curl` examples in [installation.md](installation.md#checks).

### `events` data (`DATA_EVENTS`)

New events for polling. Parameters: `after` (optional) = the `cursor` of the previous page.

First request, without a cursor:

```json
{ "key": "events", "companyId": "<company-id>", "params": {} }
```

Response:

```json
{
  "data": {
    "records": [
      { "id": "4b1f…", "at": "2026-03-10T00:43:02.000Z", "kind": "handoff", "issueId": "e2a0…",
        "identifier": "ACME-62", "title": "React page for the org chart", "parentId": "f310…",
        "from": { "kind": "agent", "id": "77aa…", "name": "Laura" },
        "to": { "kind": "agent", "id": "90bb…", "name": "Jamal Brooks" },
        "actor": { "kind": "agent", "id": "77aa…", "name": "Laura" },
        "statusFrom": null, "statusTo": null }
    ],
    "cursor": "seq:3f9a12c0:57",
    "snapshotAt": "2026-03-10T00:51:20.000Z"
  }
}
```

Next request:

```json
{ "key": "events", "companyId": "<company-id>", "params": { "after": "seq:3f9a12c0:57" } }
```

Rules (`pageEvents` in `src/worker/feed.ts`):

| Cursor | Response |
| --- | --- |
| absent | the last 20 records, oldest first |
| `seq:<epoch>:<n>` from the same worker run | the records published after `n`, oldest first, at most 50 |
| `seq:…` from a previous run (the worker restarted), or with `n` beyond the last record | same as without a cursor: the last 20 |
| ISO date (old format) | the records with `at` later than the date minus 15 s, at most 50 |

The cursor is opaque: just pass it back. Records are in publication order, which does not always coincide with `at`. A page can repeat records already seen (after a restart or with an ISO cursor): the reader deduplicates by `id`. With nothing new, `records` is empty and `cursor` stays valid.

`snapshotAt` is the `generatedAt` of the worker's latest snapshot: if it is more recent than the one shown, the UI requests `snapshot`.

### `ping` action (`ACTION_PING`)

Publishes a `ping` record and recomputes the snapshot. It is used to check that worker, state and polling work without creating tasks.

```json
{ "key": "ping", "companyId": "<company-id>", "params": {} }
```

Response: `{ "data": { "ok": true } }`. The page shows "Test event: worker and page are connected". The UI has no button for `ping`: it is called from the bridge.

### `refresh` action (`ACTION_REFRESH`)

Expires the caches for agents, settings and parents, rebuilds the model and returns the new snapshot (same shape as `snapshot`). Closed tasks keep their 5-minute refresh. The page calls it every 60 s.

### `report_progress` tool (`TOOL_REPORT_PROGRESS`)

It does not go through the UI bridge: agents call it during a run. See [agents-and-percentage.md](agents-and-percentage.md).

## Stream messages (for the future)

Channel `org-flow` (`STREAM_CHANNEL`). Today the worker emits them but the host does not deliver them (501). Shape:

```json
{ "type": "event", "record": { "id": "…", "at": "…", "kind": "run_started", "actor": { "kind": "agent", "id": "…" } } }
```

```json
{ "type": "snapshot", "snapshot": { "companyId": "…", "generatedAt": "…", "people": [], "tasks": [], "groups": [], "feed": [], "settings": {}, "counts": {} } }
```

`event` goes out immediately on every record; `snapshot` after the 600 ms debounce. If the stream connects, the UI treats `event` as a page of `events` and `snapshot` as a `snapshot` response (the most recent `generatedAt` wins).

## Versioning rules

Worker and UI come out of the same build, but a browser may still hold the old UI in memory for a few minutes after an update (until the page is reloaded). Saved state, on the other hand, survives all versions. Therefore:

1. Every change to `src/shared/types.ts` is a contract change: in the same commit update worker, UI, tests and this file (the comment at the top of `types.ts` says so too).
2. Adding a field is fine. The UI must work if the field is missing (snapshot from an old worker) and the worker must not rely on new fields in saved data.
3. Renaming or removing a field, or changing its meaning, requires handling both forms for at least one version.
4. New values of `FeedKind` or `VisualState`: the UI has a default case for unknown kinds ("Event", pose `idle`); still add the explicit case in `Panels.tsx`, `presence.ts` (UI) and `POSE_FOR_STATE`.
5. Saved data (`FeedRecord` in the activity feed, `HistoryEntry`, `ReportedProgress`): a new version must read what the previous one wrote. If you change a key, also read the old one as `STATE_FEED_LEGACY` does (`recent-feed` of 0.1.0).
6. The `events` cursor is opaque: the UI must not interpret it. The worker still accepts the ISO cursors of the first 1.0.
7. Changing a bridge key or the tool name breaks the cached UI or the agents' instructions: avoid it; if necessary, register both keys for one version.
8. Record the change in [CHANGELOG.md](../CHANGELOG.md) and, if it is a choice, in [design-decisions.md](design-decisions.md).
